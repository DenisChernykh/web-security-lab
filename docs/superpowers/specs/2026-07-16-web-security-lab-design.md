# Локальная лаборатория безопасности веб-сайтов

Дата: 2026-07-16

## 1. Цель

Создать локальную учебную лабораторию, в которой пользователь последовательно наблюдает типовые уязвимости веб-приложений на реальных HTTP-запросах и изолированных намеренно уязвимых backend-приложениях.

Первая версия должна объяснять материал с базового уровня, не теряя технической точности. Пользователь видит нормальное поведение, выполняет безопасную локальную атаку, изучает ответ и объясняемые логи, переключает сервер на защищённую реализацию и повторяет тот же запрос.

Лаборатория предназначена только для локального обучения. Она не должна принимать адреса внешних целей, исполнять команды оболочки или предоставлять универсальные средства эксплуатации.

## 2. Критерии успеха

- Вся система запускается одной обязательной командой: `docker compose up --build`.
- В интерфейсе свободно доступны четыре сценария: SQL Injection, Stored XSS, IDOR и CSRF.
- Внутри каждого сценария используется одинаковый маршрут: нормальный запрос, локальная атака, разбор, включение защиты, повтор и сравнение.
- Атака воспроизводится в режиме `vulnerable` и блокируется тем же запросом в режиме `safe`.
- HTTP-запрос, ответ и структурированные события связаны одним `trace ID`; diff выбирается для той же лаборатории и активного режима.
- Данные каждой лаборатории можно вернуть в исходное состояние.
- Система сообщает отдельно о недоступности контейнера, ошибке упражнения и ожидаемом блокировании атаки.
- Контейнеры лабораторий изолированы от внешней сети и не публикуют свои порты на всех интерфейсах хоста.

## 3. Объём первой версии

### Входит

- единая учебная оболочка с меню сценариев;
- четыре самостоятельных mini-app;
- режимы `vulnerable` и `safe` в каждом mini-app;
- реальные HTTP-запросы и локальные хранилища данных;
- отдельный локальный origin для CSRF-сценария;
- поток структурированных логов в реальном времени;
- отображение HTTP-ответа и diff серверных реализаций;
- сброс состояния каждой лаборатории;
- объяснения для новичка с точными терминами;
- автоматические интеграционные и браузерные проверки.

### Не входит

- регистрация и постоянные пользовательские профили;
- баллы, достижения и обязательное последовательное открытие уроков;
- облачное или публичное развёртывание;
- сканирование сайтов и ввод произвольных URL;
- произвольные payload, shell-команды и интерактивная командная строка;
- загрузка опасных файлов, перебор паролей и дополнительные сценарии атак;
- гарантированная поддержка мобильного интерфейса как основного рабочего режима.

## 4. Архитектура

Docker Compose поднимает общую учебную оболочку, локальный gateway и четыре независимые лаборатории. Каждая лаборатория является отдельным приложением, имеет собственные данные, режим, журнал событий и операцию сброса.

Общая оболочка не содержит уязвимых обработчиков. Она отвечает только за навигацию, шаги урока, управление режимом, запуск разрешённых упражнений и визуализацию результатов.

Локальный gateway предоставляет браузеру только известные маршруты. Лаборатории не принимают адрес назначения от пользователя и не работают как универсальные proxy. Публичный listener привязывается к loopback-интерфейсу. Внутренние сервисы находятся в закрытой Docker-сети без исходящего интернет-доступа.

### Сервисы

1. `lab-console` — учебный frontend.
2. `gateway` — локальная маршрутизация к allowlisted-сервисам.
3. `sql-lab` — самостоятельное приложение с собственной реляционной базой.
4. `xss-lab` — гостевая книга с собственным хранилищем.
5. `idor-lab` — документы и два учебных пользователя с собственным хранилищем.
6. `csrf-lab` — сайт-жертва с cookie-сессией и собственными данными.
7. `csrf-attacker` — отдельный локальный origin с фиксированной атакующей формой.

Реализация может использовать встроенные базы там, где отдельный сервер базы не улучшает урок. SQL Injection использует настоящую реляционную базу и выполняет наблюдаемые SQL-запросы.

## 5. Общий контракт лаборатории

Каждый mini-app предоставляет только фиксированный учебный контракт:

- `health` — состояние готовности;
- `mode` — чтение и переключение `vulnerable`/`safe`;
- `reset` — идемпотентное восстановление seed-данных;
- `exercise` — выполнение allowlisted-действий конкретного урока;
- `events` — поток структурированных событий;
- `source` — чтение только двух заранее определённых обработчиков для diff.

Точные HTTP-маршруты определяются в плане реализации, но семантика и формат ответов должны быть единообразны для всех четырёх mini-app.

`source` не принимает путь к файлу. Он возвращает только allowlisted-файлы текущей лаборатории, чтобы интерфейс показывал реальную реализацию без возможности читать произвольные данные контейнера.

## 6. Поток эксперимента

1. Пользователь выбирает сценарий и шаг урока.
2. Console проверяет `health` соответствующего mini-app.
3. Пользователь выбирает режим `vulnerable` или `safe`.
4. Console отправляет фиксированный учебный запрос через gateway.
5. Mini-app создаёт `trace ID` и испускает события на важных границах обработки.
6. Реальный обработчик выполняет SQL-запрос, вывод HTML, проверку владельца или проверку CSRF-токена.
7. Console сопоставляет HTTP-ответ и события по `trace ID`, а исходный код — по лаборатории и активному режиму.
8. Пользователь переключает режим и повторяет тот же запрос.
9. Интерфейс сравнивает результаты и объясняет, почему поведение изменилось.

Смена режима не должна сама по себе подменять результат в frontend. Она меняет серверный обработчик, который действительно принимает следующий запрос.

## 7. Формат событий

Каждое событие содержит:

- временную метку;
- `trace ID`;
- лабораторию и текущий режим;
- источник события: browser, API, auth, database или renderer;
- стабильный тип события;
- короткое техническое наблюдение;
- объяснение простыми словами;
- результат или решение, если оно применимо;
- идентификатор шага урока.

События не содержат пароли, полные cookies, session ID, CSRF-токены и другие секреты. Для учебного SQL допускается показывать запрос и безопасные seed-значения, если это необходимо для объяснения механики.

## 8. Сценарии

### 8.1. SQL Injection

Учебное приложение содержит форму входа и несколько seed-пользователей.

- Нормальный шаг показывает формирование корректного запроса и один ожидаемый результат.
- Атака использует фиксированное учебное значение, изменяющее логическое условие SQL и позволяющее обойти проверку пароля.
- `vulnerable` собирает SQL путём конкатенации пользовательских данных.
- `safe` использует параметризованный запрос.
- Логи показывают границу между входными данными и командой, итоговую форму запроса, число найденных строк и причину результата.

### 8.2. Stored XSS

Учебное приложение представляет собой гостевую книгу.

- Нормальный шаг сохраняет и выводит обычный текстовый комментарий.
- Атака сохраняет фиксированный HTML-payload, который выполняет только безвредное DOM-действие внутри страницы лаборатории.
- Payload не читает cookies, storage или сетевые данные и не отправляет запросы наружу.
- `vulnerable` вставляет сохранённое значение как HTML.
- `safe` выводит значение как текст или использует экранирование по контексту.
- Логи связывают сохранение данных, формирование DOM и выполнение браузерного события.
- CSP объясняется как дополнительный слой, а не как замена безопасному выводу.

### 8.3. IDOR

Учебное приложение содержит двух пользователей и принадлежащие им документы.

- Пользователь входит под фиксированной учебной учётной записью.
- Нормальный шаг читает собственный документ.
- Атака меняет идентификатор и получает чужой документ.
- `vulnerable` проверяет только наличие сессии и ищет документ по ID.
- `safe` ищет документ одновременно по ID и владельцу текущей сессии.
- Логи явно разделяют аутентификацию и авторизацию.

### 8.4. CSRF

Сценарий использует сайт-жертву и отдельный локальный атакующий origin.

- Пользователь входит на сайт-жертву и видит исходное состояние профиля.
- Фиксированная форма на атакующем origin инициирует изменение состояния с cookie-сессией пользователя.
- Интерфейс показывает, что браузер может отправить запрос, даже когда Same-Origin Policy не позволяет атакующей странице прочитать ответ.
- `vulnerable` доверяет одной cookie-сессии и не проверяет доказательство происхождения действия.
- `safe` требует корректный CSRF-токен и использует подходящие атрибуты cookie как дополнительный слой.
- В уроке отдельно фиксируется: CORS не является защитой от CSRF.

## 9. Интерфейс

Основной desktop-экран состоит из трёх зон:

1. Слева — свободное меню четырёх сценариев и прогресс внутри текущей сессии.
2. По центру — текущий шаг, краткое объяснение, запрос, фиксированные учебные параметры, переключатель режима и запуск.
3. Справа — вкладки HTTP-ответа, событий и diff.

Внутри каждого сценария используется последовательность:

1. нормальный запрос;
2. локальная атака;
3. разбор событий и первопричины;
4. переключение защиты;
5. повтор и сравнение.

На узком экране зоны складываются вертикально в том же смысловом порядке. Мобильная оптимизация не должна менять или скрывать технические данные.

Визуальное направление: спокойный тёмный технический интерфейс, нейтральные поверхности, один cyan-акцент для действий и навигации, красный только для уязвимого состояния. Интерфейс не использует декоративные «хакерские» эффекты, которые мешают чтению.

## 10. Состояния и ошибки

- До запуска показывается готовность выбранного контейнера.
- Недоступная лаборатория отображается как инфраструктурная ошибка с предложением проверить Docker health, а не как неудачная атака.
- Каждый эксперимент имеет ограниченный таймаут. По таймауту интерфейс сохраняет `trace ID` и показывает последнее полученное событие.
- Ожидаемая блокировка в режиме `safe` отображается как успешный результат урока, а не как системная ошибка.
- Невалидный фиксированный ввод показывает ошибку упражнения и не отправляется как произвольный запрос.
- `reset` можно безопасно повторять; после него интерфейс заново проверяет seed-состояние.
- При потере потока событий HTTP-ответ остаётся доступен, а неполнота логов явно отмечается.

## 11. Безопасные границы

- Все опубликованные порты привязаны к `127.0.0.1` или эквивалентному loopback listener.
- Внутренние лаборатории не имеют исходящего доступа в интернет.
- Gateway маршрутизирует только к фиксированным сервисам.
- Ни один endpoint не принимает внешний host, файловый путь или команду.
- XSS-payload не читает и не передаёт секреты.
- Логи и интерфейс маскируют аутентификационные данные.
- Seed-аккаунты и данные вымышлены.
- Проект содержит явное предупреждение, что намеренно уязвимый режим нельзя публиковать в сеть.

## 12. Проверка

### Контрактные и интеграционные тесты

- общий contract suite применяется ко всем четырём mini-app;
- `health`, `mode`, `reset`, `events` и `source` соответствуют общему контракту;
- каждый сценарий проверяет положительный и отрицательный путь в обоих режимах;
- повторный `reset` приводит к одному и тому же seed-состоянию;
- source endpoint не читает неразрешённые файлы;
- события не содержат секреты.

### Браузерные тесты

- полный маршрут каждого урока от нормального запроса до сравнения;
- обновление логов и корреляция по `trace ID`;
- переключение режима действительно меняет серверный результат;
- CSRF проверяется с двумя локальными origin;
- недоступный контейнер и потеря event stream имеют отдельные состояния;
- узкий viewport сохраняет порядок и доступность всех технических данных.

### Docker smoke test

- чистый запуск выполняется одной командой;
- healthchecks всех сервисов становятся зелёными;
- наружу опубликован только локальный gateway;
- лаборатории не выполняют исходящие сетевые запросы;
- после полного reset все четыре сценария снова воспроизводимы.
